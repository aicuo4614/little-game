# Unity 战斗性能排查 — 2026-11-27

## 验证条件

Windows Editor / Unity 2022.3.62f3c1，固定540×960，seed=173，正常转盘招募/部署/奖励/十波胜利，2倍战斗速度；Application.targetFrameRate=-1、vSyncCount=0；Profiler开启，未开Deep Profile。前后十波英雄、星级和布阵坐标逐项一致。基线 before-repeat.json，优化 after-portrait.json。

注意：主线程总耗时含Editor、Profiler、MCP和系统调度；优化采样在5/8/10波额外读取Hierarchy，不能把主线程均值小幅变化当作纯游戏性能提升。全局GC含Editor，不能拿它替代PlayerLoop或业务Marker的GC。Render Thread计数器不可用(-1)，本轮未得到GPU耗时；所有结果都不是手机帧率。

## 已定位的问题与处理

1. UnitStatusControl.Until每次状态判断创建LINQ链，单位可受控/冻结检查导致View典型帧约8KB分配。改成遍历字典、复用过期键缓存；单位visualKey不再每帧拼接，无新事件时不创建事件数组。
2. TimelineEffectPlayback原来逐帧从0模拟到当前时间。实战改为增量推进（粒子关闭固定步长重采样）；首次、倒放会复位；编辑器预览仍按绝对时间。覆盖PlayEffect、PlayHit和Bullet。
3. 导航57×25=1425节点，约10912条有向边；每个单位每次最多8个候选落点，每条边又对全部动态单位做连续碰撞检查。无路时多次同步穷尽搜索，造成CPU尖峰。现对同一规划批次缓存边通行结果，首次穷尽后复用可达集合；换单位或下次规划立即失效，保持动态碰撞规则。
4. Roy最小堆Remove存在堆序维护错误，独立回归复现后修复。优先队列修复属于正确性修复，不能单独宣称它贡献了多少性能收益。

## 导航方案与Burst/Jobs判断

A*适合当前平面绕行，问题主要是当前把动态单位碰撞、攻击落点搜索和全局搜索紧耦合，且没有总扩展预算。Roy通用对象图、字典、委托和每次搜索节点分配不适合长期承担高频拥堵搜索。建议下一步先用连续数组/复用搜索状态，分离导航占位快照与连续执行校验，减少候选重复并加入可续算的总扩展预算/错峰重规划；保留阻挡等待、不推挤与确定性落点规则。此段是建议，尚未实施。

工程已有Burst1.8.21；当前Domain导航未使用Burst或Jobs。Burst是编译加速，Jobs是任务调度，不能靠加引用自动加速现有托管对象图。若下一阶段采用，建议先把无托管依赖的计算核心放AOT并验证Burst收益，再对互不依赖的快照计算批量Jobs；占位预订和最终应用保持明确顺序，避免Schedule后立即Complete造成等待。尚未接入多线程导航，也未声称Android Burst/HybridCLR通过。
