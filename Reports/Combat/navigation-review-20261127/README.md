# 战斗导航重新选型分析（2026-11-27）

状态：依据当前工程、Unity官方文档和固定提交GitHub源码作出的选型建议。原生NavMesh及新ORCA后端尚未在本项目比较测试，本文不宣称它们已实测最快，也不是已确认迁移指令。用户本次要求先找适合方案，不继续往原运行时累加局部补丁。

## 结论

首选验证和替换方向：Unity原生NavMeshAgent导航（全局多边形寻路+内置RVO局部避障），本项目只保留战斗决策、攻击落点预约、站定/等待/受控与位置结果同步。先用内置避障；只有围攻/锁定行为达不到验收，才对照成熟ORCA替代局部避障。不要同时运行两套避障器，也不先上Burst/Jobs或整套DOTS。

理由是当前战场规模小、平面简单、没有联网锁步要求；要解决的是单位互相让路和围攻站位。引擎现有导航覆盖全局路径、路径走廊、局部避障、加减速与网格约束，可减少本项目自行维护一整套通用导航的工作。该推荐考虑性能、表现、接入/维护成本与零额外购买预算；它是当前最佳候选判断，最终仍需代表场景横向验证。

## 实际需求重新核对

- 当前spawns.csv每波总出怪数：2、3、4、5、1、6、7、8、9、1。普通波最多9只，分批到场；我方人口最多9，因此当前配置同时单位上界18。旧20261125报告中的普通波10只已不适用于最新配表。
- 单层X/Z矩形战场，约11.6×5.9世界单位；庭院装饰不参与玩法碰撞，当前BattleNavigation使用空静态障碍表。背景滚动不等于导航地形每帧改变。
- 目标常变、双方目标不同、近战需要围攻落点，远程/受控单位需要站定；完全堵住时明确等待，解除阻挡后恢复；首领体型单独校验；刺客跳跃不应让普通寻路接管空中轨迹。
- 单位规则仍共用，玩家/MCP共用输入。敌我仍由同一战斗FSM决定行为；导航只决定如何抵达指定攻击位。

## 当前实现为什么不合适

57×25=1425个节点，约10912条有向边；一个单位每次最多尝试8个候选攻击位。每条搜索边又用连续碰撞对所有单位做检查，把瞬时动态人群当成全局图障碍；目标稍动、落点被占、堵路重试又触发搜索。对象图、字典、委托和搜索节点分配进一步增加成本。没有明确的全场搜索扩展总预算。

这把“去哪里站”和“怎么绕地图”及“如何避开旁边正在走的单位”混在一次昂贵搜索中。换成更快A*、单纯缩网格或加Burst都不能自动解决围攻争位、局部死锁、被挤动和大量重规划。

已确认的优化采样（Unity540×960、无限帧率、正常十波）使规则峰值从158.42ms降到19.25ms，但约18个单位的这个峰值仍不达要求。这个数据不能用来证明整个A*算法体系不适合，只能证明当前集成不合格。

## 候选比较

| 方案 | 适配判断 | 核心取舍 |
|---|---|---|
| Unity原生NavMeshAgent+战斗落点预约 | 首选验证 | 一套成熟全局/局部导航，无额外插件购买；需要做好固定步长状态回写、暂停/倍速和站定锁定，不能直接让两个位置系统争夺Transform |
| 静态路径+成熟RVO2/ORCA局部避障 | 次选对照 | 可保持纯规则求解器和明确控制；ORCA自身不能解决U形/封路全局绕行，需要配套全局路径及战斗预约，接入工作更多 |
| Aron A* Pathfinding Project Pro+ORCA | 成熟备选 | 功能完整，但局部避障是Pro功能；当前没有必要先购买，不能把Free路径功能当成包含免费RVO |
| Flow Field+Burst/Jobs | 当前不优先 | 更适合大量单位共用较少目的地；本项目单位少、目标和攻击位多且变化快，流场共享收益有限，仍需解决局部避障和站位 |
| 自研连续数组A*+自研人群求解 | 当前不优先 | 理论上可按场景极致优化，但需要自行承担几何、死锁、队列、拥挤、体型和维护验证。已有自定义集成的高成本已经暴露，不应把重写搜索内核当成解决整个系统 |
| 完全直线移动+分离力 | 不满足完整需求 | 当前空地可能最快，但不能保证U形绕行、封路恢复及不推挤站定单位，不能仅凭几毫秒演示作为最终方案 |

## 首选方案的具体边界

1. FSM负责目标、追击、交战、受控、死亡；攻击位预约按目标周边合法空间分配，位置未失效时保持，不再每次从头试八个终点。
2. NavMesh负责地图可走范围和路径走廊。重算由目标实质变化、路径失效等事件触发；不每帧无条件SetDestination。
3. 内置RVO负责移动单位的短距离让行。寻路不把每一个移动角色作为实时切洞障碍。
4. 攻击/冻结单位的锁定不能只用最高avoidancePriority冒充绝对不动。锁定代理如何表达、是否按稳定阈值转为障碍，应由站定墙/解除锁定场景决定。若采用NavMeshObstacle，仅在稳定阻挡时按需Carve；移动时不不断切洞。官方指出Carve结果有一帧延迟，Agent与Obstacle不能同时启用，否则会自避让/反复重映射。
5. 阻挡时输出零实际速度并进入Waiting，动画按实际位移；无合法攻击位则预约等待点，不能靠挤开别人抢位。
6. 导航后端只向规则层提供实际位置、速度、路径/等待原因，表现层只读。业务规则不因此直接依赖Unity组件，也不能为了维持“所有计算必须纯C#”的额外实现偏好牺牲体验。原生后端不是跨平台确定性锁步解算器，这一点需明确；当前项目未提出联网锁步需求。
7. 常规单位与Boss按各自半径烘焙/查询有效区域；用实际体型窄道测试决定agent类型，不能只把大模型缩到小半径。

## Burst/Jobs

工程已有Burst1.8.21。原生NavMesh核心不需要我们通过Burst重编译；添加引用不会加速现有Roy托管对象图。Jobs也不会减少重复搜索的总工作，并行后立即Complete仍可能在主线程等待。

若后续确定需要自定义ORCA/批量邻居计算，先把数据转为可复用的连续结构，确认真正热点，再比较单线程、Burst与Jobs三种模式。热更程序集中的Burst在普通HybridCLR版本会解释执行；要获得原生Burst收益，计算内核拟放AOT，热更经数据接口调用。此处是方案边界，尚未实施。

## 验证决定采用什么，不能只验证快

建议只让两个真正可交付候选进入同一隔离场景：Unity原生NavMeshAgent作为首选；原生路径+成熟ORCA作为必要时的第二对照。当前已验证的版本只作性能/行为基线，不继续增加运行时开关长期维护多套正式实现。

- 规模：18单位实际规模、50单位压力；当前地图尺寸、单位实际半径、相同随机种子、相同目标轨迹；Editor540×960无限帧率。稳定运行与初始化/预热开销分开报告，但不能删掉真实的重规划/拥挤峰值。
- 场景：迎面交叉、近战围Boss、远程站定墙、U形阻挡、全堵后解除、攻击位已满、目标死亡切换、连续出怪、不同体型窄道、刺客落地、冻结/解冻、暂停/倍速。
- 行为：锁定单位不被推开；不互穿；有路可绕、无路等待、解除后能恢复；不持续左右抖动；零位移不跑步；同一位不反复争抢。
- 性能：记录导航全流程的主线程/工作线程CPU、P50/P95/P99/max、稳态GC、每秒重算/节点扩展和等待时间。不能只计Schedule时间，不能用平均帧率掩盖尖峰；禁用高频MCP大快照查询干扰采样。18单位暂定工程目标P99<=1ms、真实重规划峰值<=2ms、稳态导航0B GC（目标而非已达到，需先固定PC平台）。
- 最终旧手机表现仍需要在另一次明确手机交付中复核；当前用户要求仅Unity排查，不能把Editor结果写作手机帧率。

## 当前工程和历史记录

伤害面板减半、对象池与本关13模型/27特效各一只预热已经独立验收；未受本次重新选型影响。正式导航保留最后Unity十波验证的19ms级基线，未接入数组版寻路、NavMesh或新ORCA。后续平方距离/包围框局部实验已保存到本目录experimental-broadphase.cs.txt，仅有纯规则测试，不作正式优化成果。此前性能报告中“继续优化现有Roy”的建议由本次系统级重新选型建议覆盖。

本次选型讨论未改玩法指令、参数或战斗规则，MCP无需新增玩法操作；正式采用新后端时仍必须同步get_navigation的后端、路径、阻挡原因、耗时与验证流程。当前已有累计导航耗时与逐帧诊断工具保留。没有构建手机、付费、提交或推送。
